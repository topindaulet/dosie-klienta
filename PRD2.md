# PRD: Инструмент подготовки к встрече с клиентом (рабочее название — «Досье клиента»)

**Версия:** 0.2 (черновик для оценки и обсуждения)
**Автор:** [сотрудник банка, инициатор]
**Статус:** Инструмент работает только с общедоступной информацией из открытых источников — данные из внутренних систем банка в объём не входят (см. раздел 8, Out of scope)

---

## 1. Проблема

Сотрудники банка (менеджеры по работе с клиентами) перед встречей с действующим или потенциальным клиентом вручную собирают информацию о нём из разных источников: открытых госреестров (для оценки клиента как контрагента) и внутренних систем банка (для оценки клиента как держателя продуктов). Это делается каждый раз заново, без единого шаблона, без истории, без возможности передать подготовку коллеге. Итог — потери времени и неполная/непоследовательная картина перед встречей.

## 2. Цель продукта

Дать сотрудникам отдела единый инструмент, который:
- структурирует, что нужно проверить перед встречей (чек-лист по типу клиента — физ. лицо / юр. лицо);
- даёт быстрый доступ к открытым источникам по каждому пункту;
- позволяет внести то, что сотрудник нашёл в этих открытых источниках;
- собирает всё в единый документ, который можно выгрузить и приложить к подготовке встречи.

Инструмент сознательно ограничен только общедоступной информацией (открытые госреестры, СМИ, публичные профили). Данные из внутренних систем банка (продуктовая история клиента, скоринг, банковская тайна и т.п.) в этот инструмент не вносятся — это отдельная задача с другими требованиями к безопасности, не входящая в текущий объём (см. раздел 8).

## 3. Пользователи

- **Основные:** менеджеры по работе с клиентами отдела/филиала (целевой охват — весь отдел).
- **Дополнительно:** руководитель отдела — просмотр карточек своих сотрудников для контроля качества подготовки.
- **Администратор:** представитель IT/владелец продукта — управление доступом, полями, источниками.

## 4. Функциональные требования

### 4.1 Ввод данных о клиенте
- Поля: ФИО / наименование компании, ИИН, БИН, дата встречи, цель встречи/продукт.
- Все поля необязательны — форма должна работать и с неполными данными (например, только ФИО).
- Переключатель типа клиента: «Юридическое лицо» / «Физическое лицо» / «Не уверен — показать оба».

### 4.2 Динамический чек-лист
Чек-лист перестраивается в зависимости от типа клиента и должен включать (минимум) следующие разделы — см. Приложение A с полным перечнем полей:
- Юридическое лицо (регистрационные данные, статус, суды, госзакупки, налоговая задолженность и т.д.)
- Финансовые показатели (отчётность, выручка, НДС-статус, кредитный рейтинг и т.д.)
- Физическое лицо (публичный статус, соцсети, СМИ)

Все разделы — только пункты, проверяемые по общедоступным источникам.

Для пунктов из открытых источников — кнопка/ссылка на источник (по возможности — с подставленным именем/идентификатором клиента в поисковый запрос).

### 4.3 Ручной ввод найденного
По каждому пункту чек-листа сотрудник вносит: что нашёл (текст), дату проверки.

### 4.4 Выгрузка и передача
- Экспорт всей карточки в файл Word (.docx или совместимый формат).
- Копирование краткой текстовой сводки в буфер обмена.
- Возможность переслать документ по официальным каналам банка (email/корпоративный мессенджер) — **не автоматическая отправка**, а подготовка готового файла для ручной пересылки через одобренные каналы.

### 4.5 История и совместная работа
- Карточка клиента доступна коллегам согласно ролевой модели (раздел 6).
- Хранится история изменений: кто и когда вносил/менял запись.

## 5. Нефункциональные требования

- **Размещение:** только на внутреннем сервере/портале банка. Публичный интернет-хостинг (внешние облачные сервисы, включая бесплатные form-билдеры) исключён.
- **Авторизация:** через корпоративную учётную запись сотрудника (SSO/AD), отдельных логинов/паролей не создавать.
- **Шифрование:** данные — как в хранении, так и при передаче (HTTPS/TLS, шифрование БД или чувствительных полей).
- **Доступность:** рабочие часы банка, стандартный SLA для внутренних систем — уточнить у IT.
- **Совместимость:** современные браузеры, адаптивная вёрстка (сотрудники используют инструмент и с рабочего компьютера, и потенциально с телефона перед встречей вне офиса — уточнить, разрешено ли это политикой безопасности).
- **Аудит:** полный лог действий (создание, просмотр, изменение, экспорт записи) — кто, когда, какая запись.
- **Удаление данных:** политика хранения — например, запись хранится N дней после даты встречи, затем архивируется/удаляется автоматически. Точный срок — уточнить с комплаенс (раздел 8).

## 6. Роли и доступ (черновик)

| Роль | Видит | Может редактировать | Может выгружать |
|---|---|---|---|
| Сотрудник (автор записи) | Свои карточки клиентов | Свои карточки | Да |
| Руководитель отдела | Карточки всех сотрудников отдела | Нет (только просмотр) | Да |
| Администратор/IT | Техническая администрация, без доступа к содержимому по умолчанию | Настройки системы | Нет |

## 7. Не входит в объём (Out of scope)

- **Данные из внутренних систем банка** (продуктовая история клиента, скоринг, банковская тайна, PEP-статус, санкционные списки и т.п.). Инструмент принципиально работает только с общедоступной информацией; ввод сведений из внутренних систем банка в него не предусмотрен ни в каком виде.
- **Автоматический сбор данных** с государственных реестров (egov.kz, kgd.gov.kz, sud.gov.kz, goszakup.gov.kz, dfo.kz, kase.kz и т.п.) путём скрапинга/парсинга. Причины: 1) большинство этих сайтов не предоставляет публичного API и/или требует авторизации через ЭЦП; 2) автоматизированный обход государственных порталов создаёт юридические и технические риски. Инструмент только формирует ссылки для ручной проверки.
- Автоматическая интеграция с внутренними банковскими системами — не рассматривается.
- Автоматическая отправка email/сообщений от имени сотрудника без его подтверждения.
- Мобильное приложение (нативное) — на первом этапе достаточно адаптивной веб-версии.

## 8. Открытые вопросы

1. Хранение ФИО/ИИН/БИН клиента и результатов проверки — это персональные данные независимо от того, что источник открытый. Стоит коротко свериться с комплаенс по сроку хранения и модели доступа, даже без внутренних данных банка в объёме.
2. Срок хранения записей после даты встречи.
3. Разрешён ли доступ с личных/рабочих мобильных устройств вне офиса.
4. На какой именно внутренней инфраструктуре разворачивать (уточнить у IT: стек, БД, есть ли готовая платформа для внутренних форм/приложений, которую можно переиспользовать).

## 9. Пилот и критерии успеха

- **Фаза 1 (пилот):** 2–3 сотрудника, 5–10 реальных встреч.
- **Критерии успеха пилота:** сотрудники используют инструмент перед встречей без напоминаний; время подготовки к встрече не увеличивается по сравнению с текущим процессом.
- **Фаза 2:** доработка по итогам обратной связи, подключение остальных сотрудников отдела.

## 10. Референс UI

Есть кликабельный прототип интерфейса (HTML/CSS/JS, реализован в фирменных цветах банка), демонстрирующий:
- динамическую генерацию чек-листа по типу клиента;
- ссылки на источники;
- экспорт в Word.

**Прототип использовался только с тестовыми/демонстрационными данными, не разворачивался в периметре банка и не предназначен для ввода реальных данных клиентов.** Он может быть передан разработчику как референс по UX/вёрстке для переиспользования во фронтенде реального приложения.

|---|---|

| Статус в рейтинге крупных налогоплательщиков | kgd.gov.kz |

| Сумма и число контрактов по госзакупкам | goszakup.gov.kz |

*Примечание: точные суммы уплаченных налогов по большинству компаний закрыты (налоговая тайна, ст. 30 НК РК) — соответствующего пункта в чек-листе нет намеренно.*

### A.3 Физическое лицо
